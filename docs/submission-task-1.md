# Звіт про виконання завдання: MCP-сервер

Репозиторій: https://github.com/f3man/mcp-agent/tree/task-1

## Загальний опис

Було написано свій власний MCP-сервер (`src/McpServer`, ASP.NET Core / .NET 10). Він працює над
публічним API системи публічних закупівель Prozorro. Сервер має чотири інструменти(тули):
`list_tenders`, `get_tender`, `search_tenders`, `get_company_profile`.

Для запуску та моніторингом за роботою сервера використано .NET Aspire (`src/AppHost`,
`src/ServiceDefaults`).

Сервер запущено **і локально** (командою `dotnet run`, а також через `aspire run`), **і в
хмарі** — на Azure Container Apps. Нижче — опис того, що зроблено по кожному пункту завдання, з
посиланнями на реальні перевірки.

## Частина 1. Базове розгортання

### Вибір MCP-сервера

Було взято не готовий сервер, а написали свій — `src/McpServer`. Він реалізує чотири інструменти
лише для читання даних (без запису), на основі офіційного пакета
`ModelContextProtocol.AspNetCore`.

### Розгортання сервера

Сервер запущено двома способами, як і вимагалось у завданні:

- **Локально, напряму**: командою `dotnet run --project src/McpServer` (ключ доступу задається
  через змінну середовища `MCP_API_KEY`), а також через `aspire run --project
  src/AppHost/AppHost.csproj`.
- **У хмарі**: на Azure Container Apps, командою `aspire deploy`. Адреса сервера в інтернеті:

  ```
  https://mcp-server.mangohill-8bec81a9.germanywestcentral.azurecontainerapps.io
  ```

  Усі хмарні ресурси створено в групі `rg-aspire-apphost` (підписка
  `3aa7ce12-0f0b-42d1-b16c-398ad71bff09`, регіон `germanywestcentral`): середовище Azure
  Container Apps, реєстр образів (Container Registry), Log Analytics, Application Insights і
  сам контейнер `mcp-server`.

  > ![img.png](img.png)    
  > 📸 **Рис. 1.** Azure Portal → група ресурсів `rg-aspire-apphost`

### Перевірка, що сервер працює

Сервер запускається без помилок і відповідає на запити справжнього клієнта — це перевірено і
локально, і на хмарній адресі (детальні запити нижче, у Частині 3).

## Частина 2. Налаштування роботи сервера

### Логування

Логи налаштовано через `ServiceDefaults` (OpenTelemetry) та через звичайний `ILogger` у коді.
У логах є:
- **Запуск і зупинка** — стандартні повідомлення ASP.NET Core («Application started», «Now
  listening on...»). Також є окрема перевірка на старті: якщо ключ `MCP_API_KEY` не задано,
  сервер записує критичну помилку в лог і завершує роботу — тобто він ніколи не працює без
  захисту ключем.
- **Вхідні запити** — кожен MCP-запит (`initialize`, `tools/call` тощо) логується. Якщо запит
  без ключа або з неправильним ключем — це теж окремо записується в лог як попередження.
- **Помилки** — якщо навмисно викликати помилку (наприклад, запросити `get_tender` з
  неіснуючим `tenderId`), ця помилка явно записується в лог на рівні «error», у файлі
  `TenderTools.cs`.

### Моніторинг

Моніторинг зроблено через OpenTelemetry (трейси, метрики, логи) у проєкті `ServiceDefaults`:
- **Метрики продуктивності**: кількість запитів, час відповіді, використання HTTP-клієнта.
- **Health check**: адреси `/health` та `/alive` (доступні в режимі розробки — локально та в
  `aspire run`).
- **Інструмент моніторингу**: локально — Aspire Dashboard (запускається разом з `aspire run`);
  у хмарі — **Azure Monitor / Application Insights**. Це той самий код, він просто надсилає дані
  в інше місце — залежно від того, чи задана змінна `APPLICATIONINSIGHTS_CONNECTION_STRING`.
- Кожен з чотирьох інструментів обгорнуто в окрему «Activity» (файл `ToolTelemetry.cs`) — тому
  кожен виклик інструмента видно окремо в моніторингу, а не просто як «HTTP запит».

Важливо: спостережуваність — це не тільки для хмари. Коли сервер запущено локально через
`aspire run`, все те саме (трейси кожного виклику інструмента, метрики, логи) вже доступне без
жодних додаткових налаштувань — просто в Aspire Dashboard замість Application Insights.

> ![img_8.png](img_8.png)    
> 📸 **Рис. 2.** Aspire Dashboard при локальному запуску (`aspire run`) → вкладка «Traces».

### Авторизація

Використано **API-ключ**: клієнт передає заголовок `X-Api-Key`. Його перевіряє
`ApiKeyAuthMiddleware` — і робить це **до** того, як запит потрапить будь-куди далі: і до
`/mcp`, і до `/health`. Якщо ключ `MCP_API_KEY` не налаштовано взагалі — сервер не запуститься.

### Висновки

- **Чому обрано такий спосіб розгортання**: .NET Aspire обрано тому, що ту саму інфраструктуру,
  яку ми вже описали й перевірили локально (файл `AppHost.cs`), можна перенести в Azure майже
  без змін — однією командою `aspire deploy`. Це дає мінімум зайвої роботи при переході з
  локального запуску в хмару. Ще один плюс: спостережуваність (трейси, метрики, логи) вже
  вбудована в цю ж модель — достатньо одного невеликого кроку (додати OpenTelemetry і
  налаштувати, куди надсилати дані), і той самий код однаково показує все і локально (в Aspire
  Dashboard), і в хмарі (в Azure Monitor / Application Insights) — без переписування коду.
- **Який механізм авторизації використано**: простий API-ключ у заголовку `X-Api-Key`.
  Плюс: просто зробити й достатньо для тестового проєкту з одним клієнтом. Мінус: усі клієнти
  використовують один і той самий ключ — немає способу дати кожному клієнту окремий доступ або
  забрати доступ лише в одного. Для справжнього продукту з багатьма користувачами краще
  перейти на OAuth 2.0 (наприклад, Entra ID).
- **Які інструменти логування й моніторингу налаштовано**: OpenTelemetry (трейси, метрики,
  логи) через спільний проєкт `ServiceDefaults`. Локально дані видно в Aspire Dashboard, у
  хмарі — в Azure Monitor / Application Insights. Код для цього однаковий, різниця лише в тому,
  куди надсилаються дані.
- **Які труднощі виникли і як їх вирішено**:
  - Середовище розробки (WSL) спочатку не мало доступу ні до процесів, запущених через
    Windows-версію `dotnet.exe`, ні до Docker Desktop. Вирішено: встановили окремий Linux .NET
    SDK та увімкнули інтеграцію Docker Desktop з WSL для цього середовища.
  - Для розгортання на Azure Container Apps потрібно було додати два ресурси в код AppHost
    (`AddAzureContainerAppEnvironment` та `AddAzureApplicationInsights`), про що не було
    написано в початковому описі завдання.
  - Перший запуск `aspire deploy` вимагає кількох відповідей вручну (який тенант, яку підписку,
    яку групу ресурсів і регіон обрати). У консолі без звичайного терміналу це складно
    зробити — вирішено запуском команди через псевдотерміал (`script`) з готовими відповідями.
    Після першого разу відповіді запам'ятовуються, і наступні запуски не питають про це знову.
  - Створення самого середовища Azure Container Apps (без урахування контейнера) зайняло
    близько 16 хвилин. Перевірили окремою командою (`az deployment group list`), що це
    реальний, а не «завислий» процес — просто довелося зачекати.
  - Один раз сталася тимчасова помилка (`Text file busy`) через те, що два процеси одночасно
    намагались використати той самий файл. Вирішено простим повторним запуском команди —
    Azure не створює ресурси двічі, тож продовжив з того місця, де зупинився.

### Стан хмарного розгортання

Хмарний сервер залишено працювати на час перевірки цього завдання, щоб перевіряючий міг сам
звернутися до нього. Видалити всі хмарні ресурси пізніше можна командою:

```
az group delete -n rg-aspire-apphost --yes
```
